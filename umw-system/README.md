# UMW 社内システム

Cloudflare Pages（画面＋API）と Cloudflare D1（データベース）で動く社内システムです。

| 機能 | 利用者 | URL |
|---|---|---|
| ログイン（職員用） | 全職員 | `/login.html` |
| ログイン（管理者用） | 管理者のみ | `/admin/login.html` |
| 打刻・勤怠履歴 | 全職員 | `/punch.html` |
| チャット | 全職員 | `/chat.html` |
| 勤怠管理（集計・修正・CSV） | 管理者 | `/admin/attendance.html` |
| ワークフロー（申請・承認・書式・ルート） | 管理者 | `/admin/workflow.html` |
| 社員管理（追加・仮パスワード発行・無効化） | 管理者 | `/admin/employees.html` |
| 操作ログ | 管理者 | `/admin/audit.html` |
| 初期設定（最初の管理者の作成） | 導入時のみ | `/setup.html` |

## フォルダ構成

```
umw-system/
├─ schema.sql            D1 のテーブル定義と初期データ（何度実行しても安全）
├─ wrangler.toml         Cloudflare の設定（D1 の ID を書き込む）
├─ functions/api/        API（Cloudflare Pages Functions）
│   ├─ _middleware.js    全APIの共通処理：ログイン確認・管理者確認・CSRF対策
│   ├─ auth/             ログイン・ログアウト・パスワード変更
│   ├─ attendance/       打刻・自分の勤怠
│   ├─ chat/             チャット
│   └─ admin/            管理者専用（社員・勤怠管理・ワークフロー・操作ログ・チャンネル）
├─ lib/                  API の共通部品（パスワードハッシュ、セッション、ワークフローエンジンなど）
├─ public/               画面（HTML / CSS / JavaScript。ビルド不要）
│   ├─ _headers          セキュリティ用 HTTP ヘッダー
│   └─ admin/            管理者用画面
└─ test/                 動作確認用（サイトとしては公開されません）
```

## 導入手順（初回）

### 1. GitHub にプライベートリポジトリを作ってアップロード
1. GitHub で **Private** リポジトリ（例：`umw-system`）を作成
2. このフォルダの中身をすべてアップロード（`git push` または GitHub 画面の「Upload files」）

### 2. D1 データベースを作成
1. Cloudflare ダッシュボード →「ストレージとデータベース」→「D1 SQL データベース」→「作成」
2. 名前：`umw-db`、場所：アジア太平洋（APAC）を推奨
3. 作成後に表示される **データベースID** をコピー
4. 「コンソール」タブに `schema.sql` の中身をすべて貼り付けて実行

### 3. wrangler.toml に D1 の ID を書く
`wrangler.toml` の `database_id = "ここにD1のデータベースIDを貼り付け"` をコピーした ID に書き換えて、GitHub に反映（コミット）します。

### 4. Cloudflare Pages を作成して GitHub と連携
1. Cloudflare ダッシュボード →「Workers & Pages」→「作成」→「Pages」→「Git に接続」
2. 手順1のリポジトリを選択
3. ビルド設定
   - フレームワーク プリセット：**なし**
   - ビルドコマンド：**空欄**
   - ビルド出力ディレクトリ：**public**
4. 「保存してデプロイ」

### 5. セットアップトークンを設定して最初の管理者を作成
1. Pages プロジェクト →「設定」→「変数とシークレット」→ 本番環境に **シークレット** `SETUP_TOKEN` を追加（推測されにくい長い文字列）
2. 「デプロイ」タブから最新のデプロイを「再試行（再デプロイ）」して設定を反映
3. `https://<プロジェクト名>.pages.dev/setup.html` を開き、トークン・社員ID・氏名・パスワードを入力
4. 作成後、`SETUP_TOKEN` は削除して構いません（社員が1人でもいると初期設定画面は使えなくなります）

### 6. 社員を登録
1. `/admin/login.html` から管理者ログイン →「社員管理」→「社員を追加」
2. 表示された **仮パスワード** を本人に伝える（初回ログイン時に変更が強制されます）
3. ワークフローの承認者は「部署」と「役職」で自動的に決まります。課長・部長などは **管理者権限** を付けて、部署名・役職名の表記をそろえて登録してください

### 7.（強く推奨）管理者画面に Cloudflare Access をかける
管理者画面はパスワードに加えて、Cloudflare Zero Trust の Access で二重に守るのがおすすめです（少人数なら無料枠あり）。
- Zero Trust →「Access」→「アプリケーション」→「セルフホスト」
- 対象：`<ドメイン>/admin` と `<ドメイン>/api/admin`
- ポリシー：管理者のメールアドレスのみ許可（ワンタイムPIN）

## 更新（2回目以降）
GitHub の `main` ブランチにコミットすると、Cloudflare Pages が自動でデプロイします。
テーブルを追加・変更したときは、変更用の SQL を D1 のコンソールで実行してください（`schema.sql` は何度実行しても既存データを消しません）。

## セキュリティの仕組み
- パスワード：PBKDF2-SHA256（10万回）＋ソルトでハッシュ化して保存。平文は保存しません
- セッション：推測不能なトークンを HttpOnly / Secure / SameSite=Strict の Cookie に入れ、DB にはそのハッシュだけを保存。有効期限は職員12時間・管理者8時間
- 入口の分離：管理者 API は「管理者用ログイン画面からログインした管理者」のみ利用可能（サーバー側で毎回確認）
- ログイン失敗：同じ社員IDで15分間に5回失敗するとロック（仮パスワード再発行で解除）
- 初回ログイン・再発行後はパスワード変更が必須。パスワードは8文字以上・英字と数字を含む
- CSRF 対策：書き込み系 API は同一オリジン＋JSON のみ受け付け
- 権限変更・無効化・パスワード再発行をすると、その社員の全端末を即ログアウト
- 操作ログ：ログイン、社員の変更、勤怠修正（修正理由つき）、申請・承認などを記録
- 退職者は削除せず「無効」にします（勤怠・申請の記録を残すため）

## 運用上の注意
- **リクエスト数**：Workers 無料プランは 1日10万リクエストまでです。チャットは画面を開いている間 10秒ごとに新着を確認するため、職員数が多い場合は Workers Paid プラン（月額5ドル〜）を推奨します。間隔は `public/assets/chat.js` の `POLL_MS` で変更できます
- **残業の計算**：1日8時間を超えた実働を単純合計しています。変形労働時間制・深夜・休日の割増などは就業規則に合わせて調整が必要です
- **時刻**：打刻時刻はサーバーの時刻（UTC で保存し、日本時間で表示）を使うため、端末の時計をずらしても影響しません
- **バックアップ**：D1 には「タイムトラベル」（過去30日の任意時点に復元）があります。加えて月1回程度、ダッシュボードまたは `wrangler d1 export` でのエクスポートを推奨します

## ローカルでの確認（開発者向け・任意）
Node.js 22 以上があれば、Cloudflare なしで API のテストと画面確認ができます。
```bash
node --experimental-sqlite test/api.test.mjs      # API の通しテスト（30項目）
node --experimental-sqlite test/dev-server.mjs    # http://localhost:8788/setup.html （トークン: test-token）
```
本番と同じ環境で確認する場合は `npm install` 後、`.dev.vars.example` を `.dev.vars` にコピーして `npm run db:init:local` → `npm run dev`。
