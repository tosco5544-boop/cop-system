# UMW 社内システム

Cloudflare Workers（画面＋API）と Cloudflare D1（データベース）で動く社内システムです。

| 機能 | 利用者 | URL |
|---|---|---|
| **施設の打刻端末**（施設のパソコンで開いておく。ログイン不要、氏名をクリックして打刻） | 全職員・施設長 | `/kiosk.html` |
| 事務員ログイン | 事務員 | `/office/login.html` |
| 管理者ログイン | 施設長・本部 | `/admin/login.html` |
| 勤怠管理（集計・打刻漏れ・修正・CSV） | 本部・施設長・事務員 | `/office/attendance.html` |
| 職員・打刻端末（職員の追加・端末の登録） | 本部・施設長・事務員 | `/office/facilities.html` |
| ワークフロー・チャット | 施設長・本部 | `/admin/workflow.html`・`/chat.html` |
| **延べ利用者数**（デイサービスの日次入力・月次／曜日別平均・月別推移） | 施設長・本部 | `/admin/usage.html` |
| 社員管理・操作ログ | 本部のみ | `/admin/employees.html`・`/admin/audit.html` |
| 初期設定（最初の管理者の作成） | 導入時のみ | `/setup.html` |

### 権限と見られる範囲
| 権限（社員管理で設定） | ログイン | できること | 見られる範囲 |
|---|---|---|---|
| 一般 | なし | 打刻端末で打刻 | — |
| 事務員 | 事務員ログイン | 勤怠管理、職員の追加、打刻端末の登録 | 部署が施設名 → その施設だけ／本部など → 全施設 |
| 管理者（施設長） | 管理者ログイン | 上記＋ワークフロー・チャット、打刻端末で打刻 | 自分の施設だけ |
| 管理者（本部） | 管理者ログイン | すべて（社員管理・操作ログ・施設の追加を含む） | 全施設 |

「本部」かどうかは、部署が施設名と一致しないことで判断します（例：部署＝本部）。

## フォルダ構成

```
umw-system/
├─ wrangler.toml         Cloudflare Workers の設定（D1 の ID を書き込む）
├─ schema.sql            D1 のテーブル定義と初期データ（説明コメント付き・wrangler 用）
├─ schema-console.sql    同じ内容をダッシュボードのコンソール用に1文1行にしたもの
├─ migration-006-usage.sql  既存のD1に「延べ利用者数」のテーブルと8施設を追加するSQL
├─ data/usage-2026-part1〜4.sql  延べ利用者数の過去データ（2026年1月〜11月、1,944日分）
├─ migration-002-kiosk.sql  既存のD1に「施設・打刻端末」を追加するSQL（初回導入時は不要）
├─ src/
│   ├─ index.js          Worker の入口（/api/... を各 API に振り分け）
│   └─ api/              API 本体
│       ├─ _middleware.js  全APIの共通処理：ログイン確認・管理者確認・CSRF対策
│       ├─ auth/           ログイン・ログアウト・パスワード変更
│       ├─ attendance/     打刻・自分の勤怠
│       ├─ chat/           チャット
│       └─ admin/          管理者専用（社員・勤怠管理・ワークフロー・操作ログ・チャンネル）
├─ lib/                  API の共通部品（パスワードハッシュ、セッション、ワークフローエンジンなど）
├─ public/               画面（HTML / CSS / JavaScript。ビルド不要）
│   ├─ _headers          セキュリティ用 HTTP ヘッダー
│   └─ admin/            管理者用画面
└─ test/                 動作確認用（サイトとしては公開されません）
```

## 導入手順（初回）

### 1. GitHub にプライベートリポジトリを作ってアップロード
1. GitHub で **Private** リポジトリ（例：`umw-system`）を作成（README などは追加しない）
2. このフォルダの中身をすべてアップロード（GitHub 画面の「uploading an existing file」にドラッグ＆ドロップ、または `git push`）

### 2. D1 データベースを作成
1. Cloudflare ダッシュボード →「ストレージとデータベース」→「D1 SQL データベース」→「作成」
2. 名前：`umw-db`
3. 作成後に表示される **データベースID** をコピー
4. 「コンソール」タブに `schema-console.sql` の中身をすべて貼り付けて実行

### 3. wrangler.toml に D1 の ID を書く
GitHub 上で `wrangler.toml` を開いて編集し、`database_id = "ここにD1のデータベースIDを貼り付け"` をコピーした ID に書き換えてコミットします。

### 4. Worker を作成して GitHub と連携
1. Cloudflare ダッシュボード →「Workers & Pages」→「作成」→「リポジトリをインポート（Import a repository）」
2. GitHub を接続（初回は Cloudflare の GitHub アプリをインストールし、`umw-system` リポジトリへのアクセスを許可）
3. リポジトリを選択して次のとおり設定
   - プロジェクト名（Worker 名）：**umw-system**（`wrangler.toml` の `name` と同じにする）
   - ビルドコマンド：**空欄**
   - デプロイコマンド：**npx wrangler deploy**（初期値のまま）
   - ルートディレクトリ：**/**（空欄）
4. 「デプロイ」→ 完了すると `https://umw-system.<アカウント名>.workers.dev` で開けます

### 5. セットアップトークンを設定して最初の管理者を作成
1. Worker →「設定」→「変数とシークレット」→「追加」で、種類 **シークレット**、名前 `SETUP_TOKEN`、値に推測されにくい長い文字列を入れて「デプロイ」
2. `https://<WorkerのURL>/setup.html` を開き、トークン・社員ID・氏名・パスワードを入力
3. 作成後、`SETUP_TOKEN` は削除して構いません（社員が1人でもいると初期設定画面は使えなくなります）

### 6. 職員を登録し、施設のパソコンを打刻端末にする
1. `/admin/login.html` から管理者ログイン（または事務員ログイン）→「職員・打刻端末」
2. 施設の欄に **氏名を1行に1人ずつ** 入力して「追加」（社員IDは K0001 から自動。職員はログイン不要＝打刻のみ）
3. 施設の打刻用パソコンのブラウザで事務員または管理者がログイン →「この端末を『○○』の打刻端末にする」を押す（登録はそのブラウザだけに有効。Chrome などで開いたままにしておくか、ブックマークしておきます）
   - 登録すると管理者は自動でログアウトし、打刻画面（`/kiosk.html`）に切り替わります。以後はログイン不要です
   - パソコンを入れ替えたとき・ブラウザのデータを消したときは、もう一度登録してください。不要になった登録は「解除」で使えなくできます
4. 施設長・本部などの管理者は「社員管理」で追加し（施設長は 部署＝施設名、役職＝施設長、権限＝管理者）、表示された仮パスワードを本人に伝えます。施設長はその施設の打刻端末にも名前が表示され、職員と同じように打刻できます

### 7.（推奨）管理者画面に Cloudflare Access をかける
独自ドメイン（例：`system.example.co.jp`）を Worker に設定すると、Cloudflare Zero Trust の Access で `/admin` と `/api/admin` だけを管理者のメールアドレスに限定できます（パスワードとの二重防御。少人数なら無料枠あり）。
※ workers.dev の「Cloudflare Access を有効化」はサイト全体にかかり、一般職員も入れなくなるため使わないでください。

## すでに schema.sql を実行済みのD1に今回の機能を追加する場合
D1 のコンソールで `migration-002-kiosk.sql` の中身を貼り付けて実行してください（施設・打刻端末のテーブルと13施設が追加されます。既存データは変わりません）。

## 会議室・設備利用申請を削除する（既存のD1）
初期データの「会議室・設備利用申請」と「総務確認ルート」は不要になったため、新しい schema.sql からは外しました。すでに実行済みの場合は、D1 のコンソールで `migration-003-remove-meeting-room.sql` を実行するか、ワークフローの［申請書式］［承認ルート］から削除してください。

## 承認ルートを「施設長 → 事業部長」に変更する（既存のD1）
新しい schema.sql の初期ルートは「施設長承認 → 事業部長承認（→ 10万円以上で経理確認 → 100万円以上で社長決裁）」です。すでに実行済みの場合は、D1 のコンソールで `migration-004-shisetsucho-route.sql` を実行してください（役職が「所長」の社員も「施設長」に変わります）。
承認者は役職名で探すため、社員管理では施設長の役職を「施設長」、部署を施設名と同じ表記で登録してください。

## 事務員の権限を追加する（既存のD1）
すでに schema.sql を実行済みの場合は、D1 のコンソールで `migration-005-clerks.sql` を実行してください。

## 延べ利用者数（旧「延べ利用者数アプリ」を統合）
- 管理者ログイン（施設長・本部）だけが使えます。事務員・一般職員は使えません。
- 入力：本部は全施設、施設長は自分の施設だけ（延べ利用者数の施設名と、社員の部署＝施設名が同じもの）。閲覧・集計は全施設。
- 設定（施設名・定員・午前／午後／7Hの区分）：本部のみ。
- 集計ルールは元のアプリと同じです（営業日数＝入力がある日の数、3H平均＝午前平均と午後平均の平均、日曜は休業日）。
- 元のアプリのアカウント（0001〜0010）は使いません。社内システムのログインに統一しました。

### 導入（既存のD1）
1. D1 のコンソールで `migration-006-usage.sql` を実行（テーブルと8施設。schema.sql を新しく実行する場合は不要）
2. 過去データを入れる場合は、`data/usage-2026-part1.sql` 〜 `part4.sql` を順番にコンソールで実行（1回が約45KB。何度実行しても同じ日の値で上書きされるだけです）

### 注意
- 施設一覧にない部署の管理者は「本部」扱い（全施設）になります。施設長を登録するときは、部署を施設名と同じ表記にしてください。

## 親会社T社の拠点（籠上・本社・金谷・山梨）を追加する（既存のD1）
施設に「会社」の区分を追加し、T社の4拠点を登録しました。D1 のコンソールで `migration-007-tsha.sql` を実行してください（既存の13施設は会社＝G社になります）。
- ［職員・打刻端末］は会社ごとに見出しで分かれます。施設の会社は本部が「名前変更」から変えられます。
- ［勤怠管理］の絞り込みで「G社 すべて」「T社 すべて」を選ぶと、会社単位で集計・CSV出力できます（CSVには会社の列もあります）。
- 延べ利用者数の「籠上」は、施設「籠上」と同じ名前なので、籠上の施設長（部署＝籠上）が入力できます。

## 会社の構成（G社・親会社T社・孫会社F社）
- 既存の13施設は G社、籠上・本社・金谷・山梨は T社です。
- すでに migration-007 を実行して会社が「UMW」になっている場合は、`migration-008-company-names.sql` を実行して「G社」に直してください。
- F社の拠点は、本部の管理者が［職員・打刻端末］→「施設を追加」で、会社に「F社」を選んで追加します。

## 休暇申請の削除（既存のD1）
有給などの休暇申請はこのシステムでは扱わないため、「休暇申請」の書式と「一般承認ルート」を初期データから外しました。すでに実行済みの場合は `migration-009-remove-leave.sql` を実行するか、ワークフローの［申請書式］［承認ルート］から削除してください。

## 承認ルートの指定（申請ごと）と記録
- 申請画面の右側で、承認者（管理者＝施設長・本部）と順番を申請ごとに指定します。ステップ名も変えられます。
- 「ルートを呼び出す」から、書式の標準ルート（ひな形）や、これまでに使われたルートを呼び出せます。新規申請の最初は、前回この書式で自分が使ったルート（なければ標準ルート）が入っています。
- 申請すると、使われたルートが［承認ルート］画面の「使われた承認ルートの記録」に残ります（同じ並びは回数を数えます）。各申請の承認ルートと承認履歴も申請ごとに残ります。
- 既存のD1には `migration-010-route-log.sql` を実行してください。

GitHub の `main` ブランチにコミットすると、自動でデプロイされます（Workers Builds）。

## セキュリティの仕組み
- パスワード：PBKDF2-SHA256（10万回）＋ソルトでハッシュ化して保存。平文は保存しません
- セッション：推測不能なトークンを HttpOnly / Secure / SameSite=Strict の Cookie に入れ、DB にはそのハッシュだけを保存。有効期限は職員12時間・管理者8時間
- 入口の分離：管理者 API は「管理者用ログイン画面からログインした管理者」のみ利用可能（サーバー側で毎回確認）
- ログイン失敗：同じ社員IDで15分間に5回失敗するとロック（仮パスワード再発行で解除）
- 初回ログイン・再発行後はパスワード変更が必須。パスワードは8文字以上・英字と数字を含む
- CSRF 対策：書き込み系 API は同一オリジン＋JSON のみ受け付け
- 権限変更・無効化・パスワード再発行をすると、その社員の全端末を即ログアウト
- 操作ログ：ログイン、社員の変更、勤怠修正（修正理由つき）、申請・承認などを記録
- 退職者は削除せず「無効」にします（勤怠・申請の記録を残すため）

## 運用上の注意
- **リクエスト数**：Workers 無料プランは 1日10万リクエストまでです。チャットは画面を開いている間 10秒ごとに新着を確認するため、職員数が多い場合は Workers Paid プラン（月額5ドル〜）を推奨します。間隔は `public/assets/chat.js` の `POLL_MS` で変更できます
- **残業の計算**：1日8時間を超えた実働を単純合計しています。変形労働時間制・深夜・休日の割増などは就業規則に合わせて調整が必要です
- **時刻**：打刻時刻はサーバーの時刻（UTC で保存し、日本時間で表示）を使うため、端末の時計をずらしても影響しません
- **バックアップ**：D1 には「タイムトラベル」（過去30日の任意時点に復元）があります。加えて月1回程度、ダッシュボードまたは `wrangler d1 export` でのエクスポートを推奨します

## ローカルでの確認（開発者向け・任意）
Node.js 22 以上があれば、Cloudflare なしで API のテストと画面確認ができます。
```bash
node --experimental-sqlite test/api.test.mjs      # API の通しテスト（30項目）
node --experimental-sqlite test/dev-server.mjs    # http://localhost:8788/setup.html （トークン: test-token）
```
本番と同じ環境で確認する場合は `npm install` 後、`.dev.vars.example` を `.dev.vars` にコピーして `npm run db:init:local` → `npm run dev`（wrangler dev）。
